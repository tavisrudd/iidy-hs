The =!$parseYaml= tag parses a YAML string inside a template. In
=src/Iidy/Yaml/Resolution/Resolver.hs= (=resolveParseYaml=, lines 836-844) the
parsed AST goes through =astToValueRaw :: YamlAst -> Value= (line 908) and
then =fromValue=. The intermediate is an aeson =Value= whose object keys are
held in aeson's =KeyMap=, which does not keep document order (the comment on
=fromValue= in =src/Iidy/Yaml/OValue.hs= line 46 claims it preserves order,
which only holds for an already-ordered source). The ordered type is
=OValue= (=OObject ![(Text, OValue)]=, same file, line 27). The Rust
original resolves the tag in =~/src/iidy/src/yaml/resolution/resolver.rs=
(=resolve_parse_yaml=, around line 1820) with =serde_yaml::from_str= into
=serde_yaml::Value=, whose mappings keep source order, so mapping keys come
out in source order there. If the Haskell result reorders keys, rendered
templates differ from Rust. Flagged in the March Gemini review of the
resolver error paths and confirmed as still present by the C2 triage
([[file:../C2/report--handoff-triage.org][report]]).

Other callers of =astToValueRaw= have the same loss: =resolveEscape=
(Resolver.hs line 861), =parseYamlContent= in
=src/Iidy/Yaml/Imports/ContentParsing.hs= (line 48) and
=src/Iidy/Cfn/Operations/ConvertStack.hs= (line 193). They are not part of
this card.

Existing tests: the =parseYamlTests= group in =test/Test/ResolverTest.hs=
(line 951) uses =assertResolves= and already compares =OObject= lists, so an
ordering test fits there; end-to-end fixtures live under
=test-fixtures/example-templates/= with matching =expected-outputs/=.
