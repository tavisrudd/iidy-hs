Found by [[file:../C25/index.org][C25]] (its side findings). For a
document whose keys are not in alphabetical order, Rust =get-import= prints
the keys in document order and iidy-hs prints them sorted. Reproduced on
2026-11-16 with the Rust binary (=~/src/iidy-hs/iidy-rs=) on a file
=z: [1]\na: 2\n=, and on nested =k: {z: 1, a: 2}=:
- Rust, default YAML format: =z= before =a=, and nested =z= before =a=
  (the same for a =.json= file ={"z": 1, "a": 2}=: Rust parses JSON as
  YAML and keeps its order).
- Rust =--format json=: sorted (={"a":2,"z":[1]}= pretty-printed), because
  it goes through =serde_json= (=yaml_to_json_value=).
- Rust =--query=: the result is sorted too (=--query k= prints =a= before
  =z=; =--query '@'= sorts the whole document), because the query runs on
  the =serde_json= form (=~/src/iidy/src/cfn/get_import.rs:45-64=).
So only unqueried YAML output keeps document order; JSON and queried output
are sorted in both tools, and must stay as they are. The iidy-hs binary in
the repository root predates C25, so rebuild before comparing.

Where the order is lost: =ImportData= (=src/Iidy/Yaml/Imports/Types.hs=
lines 34-39) holds =idDoc :: Value=, an aeson value whose objects are
sorted. The YAML loaders build it with =parseYamlContent= in
=src/Iidy/Yaml/Imports/ContentParsing.hs= line 48, which calls
=astToValueRaw=; =astToValueRaw= is =toValue . astToOValueRaw=
(=src/Iidy/Yaml/Resolution/Resolver.hs= lines 913-929), and
=astToOValueRaw= already keeps source order, so the owner to reuse exists
and the order is dropped only by the =toValue= step. JSON files, and
=:json= SSM values, go through =parseJsonContent= (aeson), which also loses
order. =GetImport.emitDoc= (=src/Iidy/GetImport.hs= lines 129-144) then
emits =fromValue= of the sorted value.

Who depends on =ImportData=: the parse loaders (=Loaders/File.hs= line 44,
=S3.hs= line 59, =Http.hs= line 74, =Ssm.hs= lines 62 and 197) call
=parseByExtensionStrict= and the format-suffix parsers; every other loader
(=Cfn.hs=, =Random.hs=, env, git, filehash) builds an =ImportData=
directly; the engine reads =idDoc= (=src/Iidy/Yaml/Engine.hs= lines 182 and
199) for =$params= and nested preprocessing; tests construct it in
=EngineTest= and =ImportTrustTest= and read =idDoc= in =FilehashTest= and
=ImportLoaderTest=. =astToValueRaw= is also used by
=Cfn/Operations/ConvertStack.hs= line 193 and in =Resolver.hs= itself.

Design choice (the worker decides, recording why): preferred is a new field
on =ImportData= (for example =idOrdered :: !(Maybe OValue)=) filled by the

key order, with =Nothing= meaning "use =fromValue idDoc=" and =idDoc=

changing =idDoc= to =OValue=, touches every consumer above and is not
preferred. If keeping JSON order needs a YAML-based parse that could change
the values existing JSON imports produce (numbers, duplicate keys), keep the
aeson value for =idDoc= and use the new parse for the ordered field only.
