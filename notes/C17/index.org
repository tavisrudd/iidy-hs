A stack-args file can compute its =Profile=, =Region= and =AssumeRoleARN=
from imports. The deploy commands build a first AWS environment from those
fields before preprocessing the file (=runCfnWithArgs= in
=src/Iidy/Cfn/Runner.hs= lines 64-70: =extractRawAwsFromFile=,
=mergeAwsSettings=, =createAwsEnvFromSettings=, every exception swallowed;
the raw field
reading is =resolveRawField= in =src/Iidy/Cfn/StackArgsLoader.hs= lines
199-208), so imports in the stack-args file run under the ambient
credentials and region rather than the ones the file finally names,
silently. The final environment is built later from the preprocessed values
(=Runner.hs= line 77, =loadStackArgs= lines 143-151 of the same loader).
The review quoted the loader as =src/Iidy/StackArgsLoader.hs=; the file is
=src/Iidy/Cfn/StackArgsLoader.hs=.

Rust does not have this feature: =load_stack_args=
(=~/src/iidy/src/cfn/stack_args.rs:181-262=) preprocesses with
=preprocess_yaml= first, whose =ProductionImportLoader::new()=
(=src/yaml/engine.rs:578=) has no AWS config, so an =ssm:=, =cfn:= or =s3:=
import in a stack-args file fails there with "AWS configuration required"
(=src/yaml/imports/loaders/mod.rs:72-93=); it reads
=Profile=, =Region= and =AssumeRoleARN= from the preprocessed value only.
Imports under a computed profile are therefore an iidy-hs extension, and
"matches Rust" cannot be the tie-breaker. See
[[id:org:01a1e68e-1585-707c-91d5-94cc843d0bd6][Medium: stack-args imports can run under different credentials]].
