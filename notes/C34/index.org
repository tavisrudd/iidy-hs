* Context
:PROPERTIES:
:ID: org:01a1e6fd-7d6c-773c-9a4e-30c06431e02b
:ADDED: [2026-11-16 Mon 17:52]
:END:

iidy-hs accepts a mapping with a repeated key silently (the last value
wins), in templates, stack-args and imported YAML or JSON documents. Rust
rejects it (=Failed to parse YAML from F: duplicate entry with key "z"=,
and the same with "JSON" for =.json= files), and the TypeScript original's
js-yaml rejects duplicated mapping keys too. Found by
[[file:../C28/index.org][C28]] (see its question). Rust parity is the
project default and both originals agree, so this is a parity fix; it is
user-visible because templates with duplicate keys stop rendering.

Rust does not reject duplicate keys everywhere the card assumes. Checked
with ~/src/iidy/target/debug/iidy render, local files only:
- Top-level template with =z: 1= then =z: 2=: accepted, last value wins
  (output =z: 2=). Same for a nested mapping and a stack-args file, and
  the template's own =Resources:= repeated. Rust's template parser is
  tree-sitter based; only serde_yaml/serde_json reject.
- Imported YAML file (=$imports: d: dup.yaml=): rejected with
  =Failed to parse YAML from dup.yaml: duplicate entry with key "z"=.
- Nested in an imported YAML: =Failed to parse YAML from nest2.yaml: b:
  duplicate entry with key "c" at line 2 column 4=.
- Imported =.json=: =Failed to parse JSON from dup.json: duplicate entry
  with key "z" at line 1 column 16=.
- Imported YAML repeating =<<=: rejected as duplicate key "<<". A single
  =<<= in a top-level template is rejected with the "merge keys are not
  supported in YAML 1.2" message (separate rule).
- Imported YAML with ="a"= after =a= (same string): rejected; =1= and
  ="1"= are distinct keys: accepted.
- =!$parseYaml= with duplicate keys: fails (message just "resolving
  !$parseYaml tag"). =!$parseJson '{"a":1,"a":2}'= is accepted, last wins.
So "Parser.hs rejects everywhere" would make iidy-hs stricter than Rust for
top-level templates and stack-args (the TypeScript js-yaml behaviour, but
Rust parity is the project default). Question: (a) match Rust: reject only
in imports (YAML and JSON files, SSM yaml/json) and =!$parseYaml=, leaving
top-level templates and stack-args lenient (needs a strict flag on
parseYaml, still one owner); or (b) reject everywhere as the card says,
recording the divergence in DIVERGENCES.md (outside allowed paths)? I
recommend (a). No code changed; nothing committed. Temp dir:
.supervisor/tmp/claude-C34.Qn3o96 (Rust repro files).

- Strict paths: File, Http, S3 loaders via =parseByExtensionStrict= (yaml,

  !$parseYaml (Resolver.hs:842). Lenient on purpose: =parseYaml= in Render,

  =!$expand= re-parse (all re-read already-accepted text), Engine.hs:273
  (re-parse of an import that already passed the strict parse), and SSM path
  =parseByFormatSuffixLenient= (falls back to a string on error, which is what
  Rust ssm.rs does). !$parseJson stays lenient, as Rust.
- JSON: Set check is per object (nested objects get their own set; sibling
  objects reusing a key are fine), O(n log n); aeson decodes escapes first so
  ={"a":1,"a":2}= is rejected (verified by running a local render).
- Key identity, run against the Rust binary and iidy-hs (local imports only):
  agree: =a= vs ="a"= (reject), =1= vs ="1"= (accept), =true= vs ="true"=
  (accept), =true= twice, =null= vs =~= (reject), =null= vs ="null"= (accept),
  =1.5= vs =1.50=, alias key reused (reject), flow mapping duplicate, ={}=
  =? a= explicit key, repeated =<<=.

Defects:
1. Medium. Numeric key identity is by value, Rust's is by spelling class.
   =1= with =1.0=, =1= with =1e0= are accepted by Rust and rejected here;
   =1= with =01= is accepted by Rust (=01= is a string) and rejected here
   (HsYAML resolves =01= to the number 1). Only =1= with =0x1= is rejected by
   both. Failure: a valid import with keys =1= and =1.0= or =01= stops
   loading. Smallest fix: key the number case on the scalar's source text
   class (integer vs float) or document it; the =01= case may be a
   pre-existing scalar-resolution difference worth its own card.
2. Low. Complex (sequence or mapping) keys are skipped (=keyIdentity=
   returns Nothing); Rust rejects =? [1]= twice ("duplicate entry in YAML
   map"). Rare; add a structural key to KeyIdentity or note it.
3. Low. DIVERGENCES.md entry is accurate for what it says (message prefix,
   nested path, JSON position) but omits defect 1 and 2 behaviour and that
   labels differ (Rust: =null key=, =`true`=; here =null=, =true=). Also the
   YAML column in the message is 0-based ("line 2 column 0" for a key at the
   start of line 2); Rust's columns are 1-based. Add both to the entry or
   print posColumn + 1.
Also changed without mention: every imported YAML syntax error now reads
"<msg> at line L column C" instead of =show ParseError= (describeParseError);
fine, but is a visible message change for non-duplicate errors.

Pre-existing (not this commit): a key =true= and a key ="true"= in one
mapping import as one output key (OValue keys are Text), so
=true: a / "true": b= renders only ='true': b=. Reproduce:
