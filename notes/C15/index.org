* Context
:PROPERTIES:
:ID: org:01a1e692-13fd-7254-9ca2-0d90b106a888
:ADDED: [2026-11-16 Mon 15:54]
:END:

A remote template (from S3 or HTTP) currently inherits all of its parent's
variables, may import =ssm:=, =ssm-path:= and =cfn:= values (read with the
user's AWS credentials), may fetch loopback and cloud instance-metadata
addresses over HTTP, and may build an import URL from any of those values.
Together these let a remote template read secrets and send them to a server
it controls. Relevant code: =src/Iidy/Yaml/Engine.hs= (around lines 170,
199 and 233) and =src/Iidy/Yaml/Imports/Loaders/Dispatch.hs= (around lines
70-77). The C4 review reproduced the variable leak against a loopback
server: [[id:org:01a1e68e-1585-707c-91d5-94ce6b11308a][High: remote templates can read secrets and exfiltrate them]].
The narrow fail-open fix is [[file:../C14/index.org][C14]].

This changes what templates are allowed to do, so users with existing
remote templates may be affected. The design needs the user's decision
before code changes.

Option (c) plus (e):
- Isolate imported documents from parent variables (all imported
  documents, matching Rust and TypeScript).
- Isolate custom-resource templates loaded from untrusted (non-local)
  locations from parent variables as TypeScript does (local custom
  templates keep them, as Rust).
- Block AWS-backed imports (=ssm:=, =ssm-path:=, =cfn:=, =s3:=) and
  loopback/link-local HTTP targets from untrusted documents, checking
  every redirect.
- Add an opt-in trust flag (=--trust-import-source PREFIX=, repeatable) so
  named sources keep today's behaviour.

This also settles question 3 of the options report: =s3:= is blocked from
untrusted documents entirely, with no same-bucket exception (S3-hosted
templates that import siblings need their bucket listed as a trusted
source), and question 4's first half: loopback and link-local only, not
private ranges.

** Remaining questions
:PROPERTIES:
:ID: org:01a1e6fe-2be7-72bd-983a-90ce477761ea
:ADDED: [2026-11-16 Mon 17:52]
:END:

Each answer is the supervisor's call, from the recommendation Tavis
accepted, unless marked otherwise.

- Question 4, which requests the address filter covers: only HTTP imports
  requested by untrusted documents (the options report's recommendation).
  Local and trusted-source documents may still fetch from loopback, for
  example a local development server. "Link-local" includes the AWS
  metadata addresses =169.254.169.254= and =fd00:ec2::254= (the second is
  not link-local by range, so it is listed explicitly), and the check also
  covers unspecified addresses (=0.0.0.0/8=, =::=) and IPv4-mapped IPv6
  forms of every blocked IPv4 range.
- Question 5, where trusted sources come from: the command-line flag only.
  No stack-args or config key; a file that could itself be imported must
  not widen trust (supervisor's call, fail-closed; no recorded
  recommendation).
- Question 5, prefix matching (supervisor's call, fail-closed; no recorded
  recommendation): a prefix must be a non-local location with a known
  remote scheme (=s3://=, =s3:=, =http://=, =https://=, =ssm:=,
  =ssm-path:=, =cfn:=), must end in =/=, and for =s3://= and =http(s)://=
  must name a bucket or host. Matching is a literal, case-sensitive text
  prefix of the document's location, so =s3:b/= and =s3://b/= are listed
  separately. Invalid prefixes are a command-line error.
- Question 6, documents loaded through =ssm:=, =ssm-path:= or =cfn:=:
  untrusted, as C14 already treats their bases (from the recommendation in
  =notes/C23/report--decisions-vs-originals.org= item 8, which leaves it
  open, and C14's fail-closed rule). A user who stores templates in SSM
  can list =ssm:/their/prefix/= as a trusted source.
- Redirects from a trusted source (supervisor's call, fail-closed; no
  recorded recommendation): a document's trust is decided from the
  location it was requested at, so a request to a URL under a trusted
  prefix may only redirect to locations that are also trusted; any other
  redirect is an error.
- The root template: a template given on the command line or as
  =Template:= in stack-args with an =s3:= or =http(s):= location is
  untrusted like any other document (supervisor's call, fail-closed; it
  follows from C14's base classification). Users list its prefix to keep
  its =ssm:= and =cfn:= imports working.
- Bare relative import from a remote document (found by C14): keep
  rejecting it and correct the documents that describe inheritance
  (=docs/SECURITY.org= "Relative Import Behavior", =docs/import-types.org=
  around lines 151 and 275, =docs/requirements/03-import-system.org=
  around line 440); the existing =DIVERGENCES.md= paragraph stays
  (supervisor's call, fail-closed; no recorded recommendation). Restoring
  Rust's behaviour would not give a remote document any capability it
  lacks, since it can write the absolute URL, so Tavis may prefer parity;
  that would be a separate card.
