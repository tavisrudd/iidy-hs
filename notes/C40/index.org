* Context

Origin: C22 decision (Tavis, 2026-11-16). C22 makes iidy-hs reject a
stack-args file that has =CommandsBefore= for =create-stack=,
=update-stack=, =create-changeset= and =create-or-update=, because today the
field is parsed and silently never run. This card is the work to run it, as
Rust and TypeScript do, once there is a trust design.

What the originals do: Rust =~/src/iidy/src/cfn/stack_args.rs:277-313=
(with =process_commands_before= from line 493) and TypeScript
=~/src/iidy-js/src/cfn/loadStackArgs.ts:137-166= (with
=src/cfn/runCommandSet.ts:11-67=) run each command through =bash -c= in the
argsfile's directory, after expanding Handlebars with the =iidy= namespace,
only for the four operations above. Rust also prints each command, sets
=iidy_profile=, =iidy_region= and =iidy_environment=, defines three bash
helper functions and fails the load on a non-zero exit.

Why it needs a trust design: the command text is shell built from stack-args
values, and stack-args values can come from imports (including remote ones
allowed for local stack-args, under the trust model C15 added in
=docs/SECURITY.org=). Running that text through bash would let a remote or
computed document execute code on the operator's machine. Porting Rust
unchanged is not acceptable without deciding which sources may contribute to
a command.

Dependencies: C22 (the refusal this card removes) and the trust model of
C15.

Decision (Tavis, 2026-11-17): Option E of
[[file:report--commands-before-design.org][report--commands-before-design.org]]
(iidy-js templates in commands, every substituted value checked against a
safe character set). Supervisor's call for the detail E left open: stdin is
inherited when it is a terminal and =/dev/null= otherwise; the rest of
"Common behaviour" in the note applies.

What E means, in order, for the four operations (=create-stack=,
=update-stack=, =create-changeset=, =create-or-update=; every other
operation ignores the field, as now):
1. Read the =CommandsBefore= entries from the raw argsfile AST. Each must
   be a plain or templated string written in the local argsfile; a tag,
   merge or imported entry is refused before anything runs (extend the
   classifier in =src/Iidy/Cfn/StackArgs/Credentials.hs=).
2. Preprocess the stack-args without the field (pass 1) to build the
   context: =iidy.{command,environment,region,profile,stackName,stackArgs}=,
   bare =region= and =environment=, and every =$defs= and =$imports= name.
3. Dry run: expand every command with =filehash= and =filehashBase64=
   stubbed; every substituted value (helper results included) must be a
   non-empty string of =[A-Za-z0-9._/:@+=,%-]= not starting with =-=.
   Any failure refuses the run before the first command starts, naming the
   entry, the expression and the value's source name.
4. Run the commands in order, each expanded again just before it starts,
   so =filehash= hashes what earlier commands built. =bash -c=, argsfile
   directory, =iidy_*= variables and the three =BASH_FUNC_iidy_*= helpers
   over the inherited environment, banners showing raw and expanded text,
   output streamed (stdout to stderr in =--output-mode json=), failure on a
   non-zero exit or a signal with the exit code and the raw command.
5. Preprocess the stack-args again with the expanded commands (pass 2), so
   imports of files the commands built are read after them (both originals
   resolve imports twice).

Steps 2 to 5 need two changes outside the allowed paths.

1. Json mode and the CLI stack name. The loader
   (=loadStackArgsWith=) gets neither the output mode nor the stack name
   given on the command line: both live in =src/Iidy/Cfn/Runner.hs=
   (=runCfnWithArgs= has =cli= and =stackNameOverride=), which calls
   =loadStackArgsBootstrapped= in =src/Iidy/Cfn/StackArgsBootstrap.hs=,
   which calls =loadStackArgsWith=. Neither file is allowed. Proposal:
   allow both for plumbing only, a small record (child stdout and banners
   to stderr in =--output-mode json=; the CLI stack name for
   =iidy.stackName=, which iidy-js takes first,
   =loadStackArgs.ts:157=) passed from =runCfnWithArgs= down to the loader.
   Without it, the in-bounds fallback is to send banners and child stdout
   to stderr in every mode (against "Common behaviour") and to take
   =iidy.stackName= from the file's =StackName= only.
2. The =$defs= and =$imports= names for the context. The preprocessor
   builds that environment (=process= in =src/Iidy/Yaml/Engine.hs=) but
   =PreprocessResult= returns only the document and the import manifest.
   Proposal: allow =src/Iidy/Yaml/Engine.hs= for one change, a
   =prVariables :: Map Text OValue= field holding that environment. The
   in-bounds fallback is a workaround in the loader: add a synthetic
   top-level key to the pass-1 AST mapping each raw =$defs= / =$imports=
   name to =!$ name=, read it out of the result and drop it; it works but
   depends on =!$= lookup rules (a dotted name) and fakes a document key.

Details I will take as follows unless told otherwise:
- =iidy.region=, bare =region= and =iidy_region= are the merged region
  (command line over the file's literal or computed =Region=); the load has
  no AWS environment, so there is no AWS-config fallback. Absent, the value
  is empty, so a ={{iidy.region}}= is refused as empty and =iidy_region= is
  set to the empty string (Rust sets it from its configured region).
- =iidy.*=, bare =region= and =environment= win over a =$defs= or
  =$imports= name of the same name (in iidy-js a def named =region=
  replaces the bare one).
- =iidy.stackArgs= is the pass-1 preprocessed document with the file's
  keys, as iidy-js (Rust serialises its =StackArgs= struct).
- =PKG_SKIP_EXECPATH_PATCH= is dropped (a Node packaging workaround).
