On 2026-11-16 the pre-commit hook (=.githooks/pre-commit=, which runs
=cabal test all ... | tail -5=) hung while committing the C1 closeout. The
=iidy-hs-test= binary sat in =futex_do_wait= with 76 threads, stdin on
=/dev/null=, for more than 8 minutes; a normal run of the suite takes under
half a second. After the binary was killed, an immediate rerun passed every
test in 0.38s, and the retried commit passed too. The commit before it, made
minutes earlier, also passed. So some test can deadlock or wait forever
intermittently. Likely candidates are tests using threads, timeouts, polling
or mock clocks (for example the watch-stack, spinner, polling and timing
tests).

Because the hook pipes through =tail -5=, the hung run shows no test names,
and tasty has no default per-test timeout, so a hang blocks a commit with no
diagnostic. Since then C23 added =--test-options=--timeout=60s= to the
=cabal test= line in =.githooks/pre-commit=, so the guard half of this card
is partly in place (the =Makefile= =test= target still has no timeout).

Leads for where a hang can come from: the suite is built =-threaded -N=
(=iidy-hs.cabal= around line 235) and no test module forks threads itself,
but the interactive renderer does.
=src/Iidy/Output/Renderers/Interactive/Types.hs= forks the spinner and timing threads (=forkIO= around lines 235 and 288) and
stops them with =killThread= inside =mask_= (=stopSpinner= around line 249,
=stopTimingTask= around line 310); =src/Iidy/Aws/Timing.hs= uses =bracket=
(around line 114). Tests that drive the renderer (for example
=test/Test/RendererOutputTest.hs=, =test/Test/ThemeVariantTest.hs=,
=test/Test/WatchStackTest.hs=) are the first suspects.

** Findings and open suspects
:PROPERTIES:
:ID: org:01a1e6b4-7d58-7513-8f84-0b9f9a39fe3b
:ADDED: [2026-11-16 Mon 16:32]
:END:
- Baseline thread picture of a healthy run under =-N= on this host: 24
  threads in =do_epoll_wait= (one IO manager per capability), 23-27 in
  =futex_do_wait= (idle RTS workers), 2-3 in =poll_schedule_timeout= (the
  timer manager's poll backend plus the RTS ticker). The first hang had 1
  in =poll=, so the ticker had probably stopped: the RTS was fully idle,
  every Haskell thread blocked, rather than one thread spinning or sitting
  in an in-flight DNS query (which would add a thread in =poll= or
  =recvfrom=).
- SIGTERM being ignored is consistent with tasty: tasty installs a SIGTERM
  handler that throws to the main thread, and the main thread then waits
  for running tests to be cancelled. A test that cannot receive the async
  exception keeps that wait, and the process, alive. The same applies to
  tasty's =--timeout=, which is implemented with an async exception, so the
  60 s hook timeout turns an interruptible hang into a named failure but
  cannot stop a test blocked inside a safe foreign call or
  =uninterruptibleMask=.
- Open suspect 1: =test/Test/TimingTest.hs= "reliableTimeProvider ..."
  tests make real network calls (DNS lookup of =pool.ntp.org= and an SNTP
  round trip, about 0.15 s here). =getAddrInfo= is a safe FFI call that
  =System.Timeout.timeout= cannot interrupt, so a stuck resolver (this host
  uses =nsncd=) would hang that test past both its own 2 s timeout and
  tasty's. This also breaks the project rule against network calls in
  tests. It does not match the idle-RTS picture above well, so it stays a
  suspect, not a cause.
- Open suspect 2: the interactive renderer's spinner and timing threads
  (=startSpinner= / =stopSpinner= in
  =src/Iidy/Output/Renderers/Interactive/Types.hs=). A test that starts a
  spinner on a TTY-flagged renderer and blocks on a handle or =TVar= while
  =stopSpinner= is masked is the other candidate; no test was seen
  blocking there.
- The first hang ran under GHC 9.10.3 inside =cabal test ... | tail -5= in
  the hook, possibly while other builds loaded the host; the attempt here
  is GHC 9.12.3, so a 9.10-only RTS issue cannot be ruled out either.

  nothing.
