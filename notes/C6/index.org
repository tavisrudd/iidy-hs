On 2026-11-16 the pre-commit hook (=.githooks/pre-commit=, which runs
=cabal test all ... | tail -5=) hung while committing the C1 closeout. The
=iidy-hs-test= binary sat in =futex_do_wait= with 76 threads, stdin on
=/dev/null=, for more than 8 minutes; a normal run of the suite takes under
half a second. After the binary was killed, an immediate rerun passed every
test in 0.38s, and the retried commit passed too. The commit before it, made
minutes earlier, also passed. So some test can deadlock or wait forever
intermittently. Likely candidates are tests using threads, timeouts, polling
or mock clocks (for example the watch-stack, spinner, polling and timing
tests).

Because the hook pipes through =tail -5=, the hung run shows no test names,
and tasty has no default per-test timeout, so a hang blocks a commit with no
diagnostic. Since then C23 added =--test-options=--timeout=60s= to the
=cabal test= line in =.githooks/pre-commit=, so the guard half of this card
is partly in place (the =Makefile= =test= target still has no timeout).

Leads for where a hang can come from: the suite is built =-threaded -N=
(=iidy-hs.cabal= around line 235) and no test module forks threads itself,
but the interactive renderer does.
=src/Iidy/Output/Renderers/Interactive/Types.hs= forks the spinner and timing threads (=forkIO= around lines 235 and 288) and
stops them with =killThread= inside =mask_= (=stopSpinner= around line 249,
=stopTimingTask= around line 310); =src/Iidy/Aws/Timing.hs= uses =bracket=
(around line 114). Tests that drive the renderer (for example
=test/Test/RendererOutputTest.hs=, =test/Test/ThemeVariantTest.hs=,
=test/Test/WatchStackTest.hs=) are the first suspects.

Build once with =scripts/guarded-build cabal build all --enable-tests=, then
loop the test binary about 30 times with =--timeout=20s=,
=--test-show-details=direct= style output (no =tail=), saving each run's
output to a log in the scratchpad. Vary =+RTS -N1=, =-N2= and the default
=-N=, and run some iterations while the host is loaded. Do not run the loop
under =guarded-build= for its whole duration (it holds the shared build
lock); take the lock only for the build.

Observation from the first hang (2026-11-16, GHC 9.10.3 build, before the
C3 move to 9.12.3): SIGTERM did not stop the hung binary; it was still alive
65 minutes later. At that point it had 76 threads (51 in =futex_do_wait=, 24
in =do_epoll_wait=, 1 in =poll=), no signals blocked or ignored. The GHC RTS
turns SIGTERM into an async exception to the main thread, so a main thread
stuck in an uninterruptible wait (=mask=-ed =bracket= cleanup, an =MVar= or
=STM= wait inside =uninterruptibleMask=, or a blocking FFI call) would explain
both the hang and the ignored SIGTERM. The process was then killed with
SIGKILL. Check whether the hang still occurs on GHC 9.12.3.
