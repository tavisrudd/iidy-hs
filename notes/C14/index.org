Templates loaded from remote locations are not allowed to use the local-only
import types (=file:=, =env:=, =git:=, =filehash:=, =filehash-base64:=).
The check is =isRemoteBase= in =src/Iidy/Yaml/Imports/Types.hs= (around
lines 81 and 122), which treats a parent as remote only when its location
starts with =s3://=, =http://= or =https://=. A document loaded through the
short form =s3:bucket/key= (=src/Iidy/Yaml/Imports/Loaders/S3.hs= around
lines 38, 66 and 127 keep that spelling as the base), or through =ssm:= or
=cfn:=, therefore counts as local, and a remote template can reach local
files, environment variables and git data by importing one. Found and
confirmed by the C4 review: [[id:org:01a1e68e-1585-707c-91d5-94cf1de05539][High: import trust gate fails open]].
The redesign of what remote templates may do at all is
[[file:../C15/index.org][C15]]; this card is the narrow fix.

** Question for supervisor

The stop rule "would block an import that a local template uses today"
is hit by one narrow case the Done-when list settles the other way. A
local file base whose text has a colon before any =./= or =/= prefix
now parses as an unknown prefix and is untrusted, so that file loses its
local-only imports. Examples: running =iidy render a:b.yaml=, or a nested
file =dir/x.yaml= importing =./c:d.yaml= whose resolved base is
=dir/./c:d.yaml= and which itself has =$imports=. Before the fix (and in
Rust) these counted as local. Imports written as =c:d.yaml= were already
rejected as an unknown type. Options: (a) keep the strict rule the card
states (current branch); (b) also treat a base as local when the text
before its first colon is not URI-scheme shaped (contains =/=, for
example), which fixes the nested case but not =a:b.yaml=. No loader
produces a remote location with such a prefix, so (b) stays fail-closed
for every real remote spelling. Which one?

** Decision: option (b), by URI scheme syntax (supervisor's call)
:PROPERTIES:
:ID: org:01a1e6a9-c655-7156-8262-e91ad61dc5e7
:ADDED: [2026-11-16 Mon 16:20]
:END:
Supervisor's call: a base is local when =parseTypePrefix= gives a plain
path or =file:=, or when the text before its first colon is not an RFC 3986
scheme (=ALPHA *( ALPHA / DIGIT / "+" / "-" / "." )=); such a prefix can
only come from a local path. Implemented in =isLocalBase= with a helper
=isUriScheme= in =Types.hs=, no second parser (7b1c349). The nested base
=dir/./c:d.yaml= is now local; scheme-shaped unknowns such as =ftp://= and
=a:b.yaml= stay untrusted. Accepted consequence: a local template loaded
as =a:b.yaml= (no =./=) cannot use the local-only import types; Rust treats
it as local. Recorded in the =DIVERGENCES.md= entry. Tables extended:
=a:b.yaml= in the untrusted bases, =dir/./c:d.yaml= in the local bases.
Full suite on the rebased tip: all 1592 tests pass.
