[[file:../C25/index.org][C25]] noted that iidy-hs accepts =get-import
--format yaml-cloudformation= while Rust rejects it. That is only true
below the command line: the parser already rejects it. On 2026-11-16,
=getImportFormatReader= (=src/Iidy/Cli/Parser.hs= lines 881-890, used at
line 757) accepts only =json=, =yaml= and =yml= (case-insensitive) and
fails with "Unknown output format: X. Valid formats: json, yaml"; a test
(=CliParserTest= "get-import --format yaml-cloudformation is rejected")
pins that. What remains is what is left of the difference:
- =GetImportArgs.giaFormat= (=src/Iidy/Cli.hs= line 303) is the shared
  =RenderFormat= (=RenderJson | RenderYaml | RenderCfnYaml=, line 141) that
  =render= also uses (=raFormat=, line 294, parsed by =renderFormatReader=,
  which must keep accepting =yaml-cloudformation=). So =emitDoc= in
  =src/Iidy/GetImport.hs= (lines 139-141) still has a =RenderCfnYaml= branch
  that the command line can never reach, and a function-level caller (tests,
  =runGetImportWith=) can still ask for it.
- Message and timing differ from Rust. Rust takes any string
  (=~/src/iidy/src/cli.rs= line 641, =pub format: String=), loads the import
  and applies the query first, then prints =Unsupported format: 'X'. Use
  'yaml' or 'json'.= on stderr and exits 1
  (=~/src/iidy/src/cfn/get_import.rs= lines 66-76). Verified with the Rust
  binary: =yaml-cloudformation= and =bogus= both give that line, exit code
  1, nothing on stdout. iidy-hs rejects before loading, with an optparse
  usage error (=error: option --format: ...=, then usage), exit code 1.
  iidy-hs also accepts =yml= and upper-case spellings, which Rust rejects.
- Docs (=docs/command-reference.md= lines 326-332) already say "=yaml= or
  =json=" for get-import; they are out of scope here.

Other commands share the type: =render --format= (=RenderArgs.raFormat=)
needs all three constructors and must not change.

Decision (Tavis, 2026-11-16): follow the TypeScript original: reject at
parse time and accept exactly =yaml= and =json= (lower case; =yml= and
other spellings are rejected, as TypeScript and Rust both do). See
[[file:../C23/report--decisions-vs-originals.org][decisions vs originals]]
item 7. The rest of this paragraph stands, minus the =yml= and
case-insensitive spellings, which are now fixed rather than recorded.

Proposed decision (as written before Tavis's decision): keep rejecting at the command line, which fails
earlier and reads better than Rust's late check, and make the type say so:
a get-import-only format type with two constructors (JSON, YAML) so the
unreachable =RenderCfnYaml= branch disappears from =emitDoc= and a caller
cannot ask for it. Record the remaining differences (message text, usage
error versus one-line error, rejection before the import is loaded,
=yml= and case-insensitive spellings accepted) in one =DIVERGENCES.md=
entry. The alternative is exact Rust parity (accept a string, check after
loading, print the Rust line); it costs a worse error for the user, so it
is not the default.
