Compilers in nixpkgs at =5d2b81a7=: 9.0, 9.2, 9.4.8, 9.6.7, 9.8.4, 9.10.3
(the default =haskellPackages=), 9.12.3 (=haskell.packages.ghc912=; 9.12.4
exists as a bare compiler only) and 9.14.1. Each package set uses the same
Hackage versions (one =hackage-packages.nix=), so the GHC choice does not
change the library versions available.

Cache check (=nix build --dry-run= of =ghcWithPackages haskellDeps= plus HLS):

| Package set | Derivations to build locally for the dep set                     | HLS                         |
|-------------+------------------------------------------------------------------+-----------------------------|
| ghc910      | the wrapper only                                                 | cached                      |
| ghc912      | 35 (amazonka-*, microlens-*, uuid, regex-tdfa, tasty-bench, ...) | cached (2.13.0.0)           |
| ghc914      | 241                                                              | 347 derivations, not cached |

GHC 9.14 is ruled out: its package set is largely uncached and HLS would be
built from source.

Decision: target GHC 9.12.3 through =haskell.packages.ghc912=. It is the
newest series whose package set and HLS nixpkgs largely caches; the 35
uncached derivations (amazonka and friends) build in a few minutes with
=--max-jobs 1 --cores 4=, and CI's magic-nix-cache keeps them after the first
run. The project compiled warning-free under =-Wall -Wcompat -Werror= on
9.12.3 with no source changes. The trade-off: =haskell.packages.ghc912= is
less exercised by nixpkgs than the default set, so a future lock bump may
find a package marked broken there; the fallback is to point =hpkgsFor= in
=flake.nix= back at =pkgs.haskellPackages=. CI (=.github/workflows/ci.yml=) builds only through
=nix develop=, so it always uses whatever GHC the flake selects; there is no
separate GHC 9.6 matrix to keep compatible.

** Held-back packages
:PROPERTIES:
:ID: org:01a1e670-895c-7747-aea5-1186941441e5
:ADDED: [2026-11-16 Mon 15:18]
:END:

The flake takes each library from the nixpkgs package set, which follows a
Stackage snapshot. Where nixpkgs also carries a newer release as a versioned
attribute, the cost of switching was measured by overriding that one package
in the GHC 9.12 set and counting the derivations the dev shell would then
build (=nix build --dry-run=):

| Package              | Newer attr                      | Extra derivations | Outcome                               |
|----------------------+---------------------------------+-------------------+---------------------------------------|
| tasty-bench          | =tasty-bench_0_5=               |        1 (itself) | upgraded to 0.5                       |
| microlens            | =microlens_0_5_0_0=             |                17 | held back                             |
| http-client-tls      | =http-client-tls_0_4_0=         |                14 | held back                             |
| crypton              | =crypton_1_1_2=                 |                23 | held back                             |
| optparse-applicative | =optparse-applicative_0_19_0_0= |               112 | held back                             |
| random               | =random_1_3_1=                  |               n/a | held back: override fails to evaluate |
| QuickCheck           | =QuickCheck_2_18_0_0=           |               n/a | held back: override fails to evaluate |

Reason for the held-back rows: each is a dependency of other packages in the
set (amazonka, tls, tasty, QuickCheck and so on), so overriding it rebuilds
those reverse dependencies from source on every machine and in CI, and moves
them onto versions nixpkgs has not tested together. =random= and
=QuickCheck= cannot even be swapped in alone. Boot libraries (=containers=,
=text=, =time=, =directory=, =filepath=, =process= and the rest) stay at
the versions GHC 9.12.3 ships, since replacing a boot library forces a
rebuild of everything above it. Packages with no versioned attribute are
already at the newest version nixpkgs provides.

The bounds in =iidy-hs.cabal= were left as they are (=base >= 4.17 && < 5=,
=tasty >= 1.4=, =tasty-hunit >= 0.10=, everything else unbounded): the
package is not published to Hackage and nix pins every version, so tighter
bounds would add maintenance without changing any build.
