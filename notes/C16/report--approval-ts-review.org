* Summary
:PROPERTIES:
:ID: org:01a1e6a6-0b3b-752b-ad7e-fd8aca1e0501
:ADDED: [2026-11-16 Mon 16:16]
:END:

The TypeScript original enforces approval on the client side by construction.
When =ApprovedTemplateLocation= is set, every deploy command renders the local
template, hashes it, and replaces the template with an HTTPS URL to the
approved S3 object for that hash. Before calling CloudFormation it fetches
that URL; if the fetch fails (object missing, or no read access) the command
stops and tells the user to run =template-approval request=. The template sent
to CloudFormation is therefore always the approved S3 object, never the local
body. This was a deliberate feature (PR #45, "Replace template URL when
ApprovedTemplateLocation is in use", January 2018), with error messages added
for create (issue #71) and for =update-stack --changeset= (issue 106).

The Rust port implemented only the two =template-approval= commands. Its
deploy request builders never read =approved_template_location=, so the local
template body is sent and approval is advisory. Its user docs nevertheless
describe a deploy-time check (step 5) that does not exist. The Haskell port
copied the Rust behaviour and docs. Both ports also added a "no diff" shortcut
in =template-approval review= that TypeScript never had: it reports the
template approved without writing the approved object, so the deploy-time
lookup (where it exists) would still fail.

** Git history and intent
:PROPERTIES:
:ID: org:01a1e6a6-0b3b-752b-ad7e-fd8663b6d9ad
:ADDED: [2026-11-16 Mon 16:16]
:END:

- =16bf034= (2017-12-22) "Template approval commands": request uploads
  =<md5>.pending=; review approves; "When a template is changed, the filename
  is changed because of the md5 hashing."
- =835f14e= (2018-01-11) "Use approved template for create/update stack",
  merged as PR #45 (=5bb74fd=, 2018-01-17) "Replace template URL when
  ApprovedTemplateLocation is in use". =93a8cc1= adds =render:= support.
- =1efefe1= (2018-02-20) "Show helpful error message on create if template
  needs approval", fixes #71. =86f6b08= (2018-05-15) adds the same message for
  =update-stack --changeset=, fixes issue 106.
- =1622091= (PR #151) filters stack-args keys for the approval commands;
  =8fced1f= (2019-12-04, PR #218) adds the SSM disable switch; =00e8d40=
  (2020-01-04) adds the cross-account ACL; =8926290= and =db225b8= (2020-2021)
  move the request to the 1 MB S3 template size limit.

The intent is clear from the history: approval is a gate that every deploy
command passes through, and the deployed template is the approved S3 object.
Because CloudFormation receives a =TemplateURL= under the approved prefix, an
IAM policy with a =cloudformation:TemplateUrl= condition on the deploy role
can make the gate hold for any tool, not just iidy.

** Edge cases in the TypeScript behaviour
:PROPERTIES:
:ID: org:01a1e6a6-0b3b-752b-ad7e-fd85a9fe0d96
:ADDED: [2026-11-16 Mon 16:16]
:END:

- The check is an HTTP GET of a presigned URL. A 403 (no read permission), a
  404, or a network failure all produce the same "not approved or no
  permission" message.
- A =Template= that is an HTTP(S) URL makes the approved-key computation
  throw (=approvedTemplateVersionLocation.ts:25=), so such stacks cannot use
  approval.
- With =UsePreviousTemplate: true= the swap still sets =TemplateURL= and
  =_normalizeUsePreviousTemplateOrParamValues= then sets
  =UsePreviousTemplate= (=stackArgsToX.ts:15=); CloudFormation rejects both
  together. Approval and =UsePreviousTemplate= did not work together.
- The URL is always the global =s3.amazonaws.com= path-style host, presigned
  for us-east-1; buckets in other regions depend on S3 redirect behaviour.
- Lint before deploy (=ef75a35=) never runs when approval is on.

* The no-diff "approved without writing the object" case
:PROPERTIES:
:ID: org:01a1e6a6-0b3b-752b-ad7e-fd82bbeef6c1
:ADDED: [2026-11-16 Mon 16:16]
:END:

TypeScript has no such case: with an empty diff it still prompts and, on yes,
writes the approved object, =latest=, and deletes the pending object
(=approval/index.ts:115-144=). Both ports added a shortcut when the pending
body equals =latest= (Rust =template_approval_review.rs:106-117=, Haskell
=TemplateApproval.hs:226-238=). The shortcut writes nothing, leaves the
pending object behind, and reports success. When does it fire? The pending
key is the hash of the body, and =latest= is the last approved body. If they
are equal, the approved object for this hash normally already exists and the
earlier "already approved" check would have returned first. The shortcut
fires when the approved object is missing but =latest= matches: the approved
object was deleted or expired, or =latest= was written some other way. In that
state any deploy-time lookup would refuse, while the review command claims the
template is approved. Under advisory behaviour the wrong report is harmless;
under any enforcing option it becomes a dead end, because rerunning review
loops on the same shortcut. Fixing it is independent of the enforcement
choice: match TypeScript (drop the shortcut, prompt, write on yes), or keep
the shortcut but perform the approve writes, since the content equals an
already approved body.

** Option A: deploy from the approved S3 object's URL (TypeScript parity)
:PROPERTIES:
:ID: org:01a1e6a6-0b3b-752b-ad7e-fd80bff34a10
:ADDED: [2026-11-16 Mon 16:16]
:END:

When =ApprovedTemplateLocation= is set, render the local template, compute the
versioned key, =HeadObject= it with the caller's credentials, and send a
=TemplateURL= for that object instead of the body. On =NotFound= stop with
the TypeScript message and the =template-approval request= command; on
=AccessDenied= say so separately (an improvement on TypeScript's single
message).

- What it gives :: The deployed template is exactly the approved bytes. An
  IAM =cloudformation:TemplateUrl= condition on the deploy role now works with
  iidy-hs instead of rejecting every deploy, which is the gate the docs
  describe.
- What breaks :: Deploys that currently pass with an unapproved template
  fail (intended). The deploy principal and CloudFormation need
  =s3:GetObject= on the approved keys. A =Template= given as an HTTP(S) or S3
  URL cannot be hashed; TypeScript errors there. =UsePreviousTemplate= must
  skip the swap (TypeScript is broken there). Lint and validation before
  deploy would see no body unless the local body is kept for linting. A
  bucket in another region needs a presigned or regional URL; Haskell has no
  presign helper, so this needs amazonka's presign or a region-aware
  virtual-hosted URL. Objects approved by iidy-js (MD5 keys) are not found
  while the ports use SHA256.
- Size :: Medium. One shared helper in =src/Iidy/Cfn/= used by the three
  builders in =RequestBuilder.hs= (and optionally =EstimateCost.hs=), an S3
  head call and URL construction (likely 100-200 lines with presign), mock
  tests for approved, missing, access denied, disabled by SSM, and
  =UsePreviousTemplate=; docs and =DIVERGENCES.md= (Rust has the gap).

** Option B: verify the local template's hash and refuse otherwise
:PROPERTIES:
:ID: org:01a1e6a6-0b3b-752b-ad7e-fd7f353aed83
:ADDED: [2026-11-16 Mon 16:16]
:END:

Same render, hash and =HeadObject= as option A, but keep sending the local
=TemplateBody= when the approved object exists.

- What it gives :: Unapproved templates are refused by iidy-hs. The body
  sent is byte-identical to the approved object (same render, same hash), so
  the content matches.
- What breaks :: The same deploys fail as in option A. IAM
  =cloudformation:TemplateUrl= policies still reject every deploy, so the
  documented IAM gate stays unusable and the check is client-side only. No
  cross-region or presign work, no =s3:GetObject= need for CloudFormation.
  Templates over 51 KB still cannot be deployed inline, whereas option A
  would allow up to 1 MB.
- Size :: Small. A helper and one call in each builder (about 50-80 lines),
  similar tests, docs.

** Option C: keep advisory and document
:PROPERTIES:
:ID: org:01a1e6a6-0b3b-752b-ad7e-fd7ecf3ed2ae
:ADDED: [2026-11-16 Mon 16:16]
:END:

Leave the deploy path as it is. Correct step 5 in =docs/command-reference.md=,
state that iidy-hs does not check approval at deploy time and that an IAM
=TemplateUrl= policy is incompatible with it, add a =DIVERGENCES.md= entry
against iidy-js, and optionally print a warning at deploy when the approved
object is missing.

- What breaks :: Nothing. Teams relying on approval as a gate keep a
  silent gap unless they read the docs, and the IAM gate stays unusable.
- Size :: Tiny (docs, plus a small warning helper if wanted).

** Recommendation
:PROPERTIES:
:ID: org:01a1e6a6-0b3b-752b-ad7e-fd7de524923f
:ADDED: [2026-11-16 Mon 16:16]
:END:

Option A. It is what iidy-js was built to do (PR #45 and the two follow-up
error-message fixes), it is the only option under which the documented IAM
gate works with iidy-hs, and the deployed template is the approved object
rather than a re-render that happens to hash the same. Use an S3 API
=HeadObject= for the check rather than an HTTP GET, keep linting the local
rendered body before the swap, skip the swap with =UsePreviousTemplate=, fail
clearly for URL templates, and fix the review no-diff path to match
TypeScript. Keep SHA256 unless Tavis needs iidy-js approved buckets to keep
working. Record the change against Rust in =DIVERGENCES.md=. If presigning or
cross-region URLs turn out to be more than a small addition, option B is a
reasonable first step that can grow into A, with C's docs fix shipped in
either case.
