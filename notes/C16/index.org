Template approval lets a reviewer approve a pending template, which is then
stored as an approved object in S3; the stack-args setting
=ApprovedTemplateLocation= names where approved templates live. The C4
review found that create, update and changeset
(=src/Iidy/Cfn/RequestBuilder.hs= around lines 69, 110 and 159) send the
local template regardless of approval, so approval is advisory only. Also,
when the review step finds no difference it reports "approved" without
writing the approved object (=src/Iidy/Cfn/TemplateApproval.hs= around line
226). The Rust port has the same gap. See
[[id:org:01a1e68e-1585-707c-91d5-94cde3b60847][Medium: ApprovedTemplateLocation is not enforced]].

The user wants this to start from what the original TypeScript iidy
(=~/src/iidy-js=, read-only) intended and does, and to discuss the design
before any change. Starting points there: =src/cfn/approval/index.ts=,
=src/cfn/AbstractCloudFormationStackCommand.ts=, =src/cfn/loadStackArgs.ts=.

Answers (supervisor's call, 2026-11-16): the 1 MB limit for templates
deployed from the approved URL is in scope, as Tavis chose to follow
iidy-js here; add it as a task before the docs task, with a test at the
boundary. Deploy-time lint stays out of C16 and goes to Tavis as a
separate question (iidy-js lints at deploy; Rust and iidy-hs do not).

- Region of the approval bucket (question for Tavis, 2026-11-16). What
  each tool uses today:
  - iidy-js: the request runs in the stack's region (=loadStackArgs.ts=
    112-133 configures AWS from the stack args, =configureAWS.ts:89-94=);
    the review forces us-east-1 (=approval/index.ts:78=); deploy signs a
    URL on =s3.amazonaws.com= for us-east-1 (=stackArgsToX.ts:35=,
    =maybeSignS3HttpUrl.ts:24-25=). The working iidy-js setup is one
    us-east-1 bucket serving stacks in every region (aws-sdk v2 follows S3
    region redirects for the request; not verified here, no
    =node_modules=).
  - Rust: the request uses the stack's region (=context.create_s3_client=,
    =src/cfn/mod.rs:398-405=, used at =template_approval_request.rs:63=);
    the review uses =--region= or else us-east-1
    (=template_approval_review.rs:248-254=).
  - iidy-hs: the request uses the stack's region (=app/Main.hs:245-247=,
    =runCfnWithArgs=); the review uses =--region= or the default chain's
    region, with no us-east-1 default (=app/Main.hs:253=,
    =src/Iidy/Cfn/Runner.hs:107-111=).
  amazonka does not follow S3 region redirects, so a request in the ports
  only works when the bucket is in the stack's region. Forcing us-east-1 as
  iidy-js would break port users whose bucket sits in a stack region other
  than us-east-1, so it is not taken without Tavis. Options:
  1. us-east-1 always, as iidy-js (breaks those port users; their objects
     stay where they are but iidy-hs stops finding them).
  2. The stack's region, as the ports' request (breaks the iidy-js layout
     for stacks outside us-east-1; review needs =--region=).
  3. The bucket's own region from =GetBucketLocation= (sent to us-east-1,
     which answers for any bucket; empty means us-east-1, =EU= means
     eu-west-1), falling back to the stack's region if the call is denied.
  Recommendation: option 3. It serves both existing layouts without moving
  any object, makes the review independent of =--region=, and costs one
  extra call plus =s3:GetBucketLocation= (optional because of the
  fallback). The task list below follows option 3.

  Decision (Tavis, 2026-11-16): option 3, the bucket's own region from
  =GetBucketLocation=, falling back to the stack's region if the call is
  denied.
